# SNTP 节点审计队列存储维护

本页是访问审计与 FlowTraffic 队列的运行维护入口；历史方案见 `superpowers/specs/2026-07-23-v2node-durable-access-audit-spool-design.md`，用户授权快照见 `panel-offline-mode.md`。本次代码修复日期为 2026-10-24，由用户构建发布、更新节点。

## 症状与已确认原因

节点在线人数不多，仍持续写盘并出现用户同步确认延迟。检查链路为审计入队/上传确认 → bbolt 写事务 → 磁盘同步 → 同盘授权快照 Sync → 用户同步 ACK。

四实例旧版 v5.0.0.85 的 access.db 约 2.5 GiB，超过 99% 为空闲页，实际待发送内容仅约 6–38 KB。默认 bbolt 每个写事务重写约 5 MiB 的 freelist；flow.db 在部分实例还有约 1.52 MiB/事务的额外成本。90 秒窗口观测到进程写盘约 21.63–27.95 MiB/s，审计和授权快照同步均有长时间等待。授权行数不等于在线人数；这些证据不能单独证明宿主硬件故障。详细脱敏现场记录在相邻 v2board 的 `docs/uniproxy-node-troubleshooting-runbook.md` 同日章节。

## 修复及边界

`common/accessaudit/spool_core.go::openBoltSpool` 为两类队列统一启用 `NoFreelistSync`，避免每次入队、Ack、Reject 重写整个空闲页清单。可重建的空闲页信息在重新打开数据库时恢复；`NoSync` 仍为 false，事件数据和事务元页继续执行正常持久化。上传确认、队列计数、容量与到期淘汰、授权快照及 ACK 顺序不变。

这项修复直接兼容现有队列，不需要删除、迁移或先压缩文件。物理文件不会自动缩小，`MaxSpoolBytes` 仍约束待发送内容而非数据库物理体积。数据库打开时会遍历存活页面、按历史页号范围重建 freelist，启动耗时和临时内存需要关注；不能以小规模本地测试保证生产 2.5 GiB 文件的打开时间。

排查工具也要识别 bbolt 元页中“未持久化 freelist”的特殊标记，不能升级后还按旧格式把该标记当作 freelist 页号。不要通过默认可写打开线上文件来做“只读诊断”。

## 已执行验证

- Go 1.26.10 / Windows amd64，`go test ./common/accessaudit -count=1` 通过。修改已有 `spool_core_test.go`，没有新增测试文件。
- 先用旧实现复现：模拟 32 MiB 历史积压释放后的数据库，两条记录入队、一次 Ack、一次 Reject，access/flow 各分配并交给事务写入器 221,184 字节页面；修复后各为 12,288 字节，减少约 94.4%。统计不含固定元页，不等于实际物理写盘量或线上延迟降幅，也没有减少 fsync 次数。
- 大量空闲页重新打开、继续写入及 `Tx.Check` 通过；本地该夹具重开约 7–9ms，仅为开发机样本。
- access/flow 均覆盖旧模式数据 → 新模式增删并提交 → 子进程直接退出、不调用 Close → 恢复 FIFO、待发送字节和拒收计数；再用当前依赖 bbolt v1.3.2 的默认选项打开，检查结构和统计，重新升级后继续写入，序号与记录不丢失。
- 进程退出测试覆盖已成功提交的数据，不是断电或虚拟磁盘缓存故障测试；尚未构建生产 Linux 二进制、部署或完成线上端到端验收。

## 更新与验收

1. 按现有发版方式构建节点版本，先更新一台有上述现象的机器，保留当前审计文件和授权快照。更新节点二进制即可，无 SQL 或面板配置修改。
2. 核实实际运行版本/提交、服务启动完成、审计队列可打开。两类队列各按实际是否启用检查，不能把未启用 flow.db 当作异常。
3. 比较相近业务量的 90 秒以上窗口：进程 write_bytes 增量、磁盘 iowait/await、审计新增 persistence_failures/dropped、队列是否继续上传消退。累计历史错误数不能当作本次新增。
4. 按相同 revision 跟踪用户变更 → 面板响应 → 节点应用/快照完成 → ACK，并验证真实代理连接。先确认一台改善，再更新其余实例；进程 active 或 HTTP 200 不能替代完整验收。
5. 若写入显著下降但仍有同步阻塞，继续查共享存储等待、快照编码/写盘和状态锁；本次没有改全量快照频率，不能承诺消除所有分钟级问题。

回退当前旧版时保留最新队列文件，只回退二进制；已验证同一 bbolt v1.3.2 默认打开会重建并保存 freelist。它会重新引入旧写放大。不能在节点已接收新事件后直接恢复旧数据库备份，否则会丢新记录或重放旧记录。更早依赖版本的兼容性不在本次验证范围。

## 可选离线压缩流程

压缩只用于回收历史空闲磁盘空间，不是启用本修复的前置条件。本次未执行生产压缩。运行中的数据库不能删除、截断或替换，也不在启动时自动压缩。

维护窗口准备经过校验的 bbolt CLI，优先与当前依赖 v1.3.2 一致；预先准备工具，避免停服后才下载安装。流程为：

1. 确认实际 spool 路径、磁盘余量和所有使用该文件的进程；安排节点停服，确认服务已停止且文件没有打开者，防止自动拉起。需要容纳原库、独立备份、工作副本和压缩结果，不能只按 pending_bytes 估算空间。
2. 为 access.db 和实际使用的 flow.db 分别制作保留权限/所有者的独立备份，再从备份制作工作副本。保留原库与备份。v1.3.2 的 compact 会以默认可写模式打开源文件，可能重写 freelist，所以源参数使用工作副本。
3. 对工作副本检查后生成不存在的新目标文件。以下是已按 v1.3.2 CLI 源码核对的参数形式；路径由维护者指定，不直接针对 live 文件执行：

   ```sh
   bbolt check /maintenance/access.work.db
   bbolt compact -o /maintenance/access.compact.db /maintenance/access.work.db
   bbolt check /maintenance/access.compact.db
   ```

4. 替换前需逐项验证源与目标所有 bucket/key/value 及 bucket sequence 一致，尤其 pending、meta/stats、schema_version；结构 check 成功本身不证明业务内容完全一致。此处给出维护流程，尚未提供或执行生产内容比对工具，未完成比对时不要替换原文件。
5. 全部验证成功后，在服务仍停止、原备份完好的条件下，于目标文件系统内原子替换并恢复属主/权限；逐库操作。启动后验证队列计数和上报。启动前可恢复备份；启动接受新事件后按前述回退限制处理。

当前推荐先更新二进制验收写放大修复，再视磁盘空间决定是否单独安排压缩。
