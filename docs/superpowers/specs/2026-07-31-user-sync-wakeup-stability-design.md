# v2node 用户同步唤醒连接稳定性设计

## 背景

生产灰度扩到 6 个及 22 个节点时，面板 WebSocket 监听队列快速增长，节点连接反复建立和关闭，新节点无法稳定回报 `user_sync_applied`。回滚到原 3 个灰度节点并完整重启 Webman 后恢复。

代码链路确认有两个相同的断线入口：

1. `runWakeup()` 拨号成功后先调用 `activatePush()`，初始追赶只要返回临时同步错误，就会关闭刚建立的连接。
2. `serveConnection()` 收到 `user_sync_dirty` 后调用 `flushPending()`，同步只要返回临时错误，读循环就退出并关闭连接。

这会把正常的增量分页、全量同步熔断或面板短时繁忙放大为全体节点的重连压力。

## 目标

- 同步追赶失败时保留当前 WebSocket，在同一连接内按服务端重试时间或 fallback 间隔重试。
- 重试等待期间继续读取 `ping` 和新的 `user_sync_dirty`。
- 始终保留最高待确认 revision；只有用户状态提交成功且 ACK 写成功后才清除。
- 重试等待期间的新 dirty 只能抬高待确认 revision，不能缩短服务端给出的 Retry-After。
- 只有拨号失败、读失败、pong 写失败或 ACK 写失败才进入断线重连和短轮询 fallback。
- 不修改面板协议、鉴权、数据库结构、用户同步数据模型或生产灰度名单。

## 方案比较

### 方案 A：原连接内重试（采用）

拨号后立即进入读循环，同时启动首次追赶定时器。同步错误只重排定时器，连接错误才退出读循环。改动集中在 v2node 状态机，协议和面板无需配套变化。

### 方案 B：同步失败后关闭 WebSocket，只增加重连退避

能够降低瞬时连接频率，但仍会在大批节点同时追赶时反复建立连接，不能消除根因。

### 方案 C：面板端限制连接或增加排队

只能保护面板，节点仍然丢失稳定连接和 ACK；适合作为后续容量保护，不替代客户端状态机修复。

## 状态与错误边界

- `connecting`：只用于拨号阶段。
- `catching_up`：WebSocket 已连接，但首次或后续用户同步尚未成功；期间正常处理 ping 和 dirty。
- `push`：最近一次追赶和必要 ACK 已成功。
- `fallback`：仅在 WebSocket 不可用时短轮询。
- `closed`：运行时退出。

同步函数返回的普通错误和 `UserSyncRetryError` 都属于追赶错误。`UserSyncRetryError` 使用其 `After`（最少 500ms，并保留稳定 jitter）；其他错误使用配置的 fallback 间隔。ACK 通道缺失或 ACK 写失败属于连接错误，立即交给外层关闭并重连。

## 测试

1. 构造同一条假连接：第一次同步失败，等待期间收到 ping 并成功 pong，第二次同步成功后 ACK 最高 revision；断言两次同步之间连接没有关闭。
2. 构造 ACK 写失败：断言读循环退出，让外层走连接恢复，而不是在坏连接上无限重试。
3. 构造 500ms Retry-After：等待期间再发送更高 revision 的 dirty，断言 revision 被合并且第二次同步不会提前发生。
4. 保留既有测试，确认失败同步不 ACK、合并最高 revision、稳定 jitter、全量同步熔断等行为不变。

## 发布边界
