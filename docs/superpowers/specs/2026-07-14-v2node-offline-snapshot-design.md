# v2node 面板失联离线快照设计

## 背景

`v2node` 当前把面板同时当作控制面和启动时的必要依赖：

- 冷启动时必须从面板取得节点配置、用户列表和在线状态，任一关键请求失败都会导致节点无法启动。
- 运行中的周期任务超时会向主进程发送 reload 信号。
- reload 会先关闭已有 controller 和代理内核，再重新请求面板；如果面板仍不可达，重载失败并退出，原本可用的数据面也随之中断。
- 本地没有持久化的最后成功状态，因此进程、机器或容器重启后无法在面板故障期间恢复服务。

目标是把控制面故障与数据面运行隔离：面板不可达时，节点无限期继续使用最后一次成功状态，不删除用户、不主动断开已有连接，也允许用户继续按旧快照建立新连接。

## 已确认的产品规则

1. 面板请求失败后立即进入离线模式，不等待 24 或 72 小时。
2. 离线模式没有强制有效期。即使失联超过 72 小时，节点也继续服务。
3. 离线期间忽略面板侧新发生的封禁、流量耗尽、权限变化和用户变更，因为节点无法可靠获知这些变化。
4. 离线期间保持最后快照的用户集合、限速、设备限制、IP 限制和远端在线统计，不依据本地时间额外删除用户。
5. 面板恢复后自动回到在线同步，应用面板最新状态并更新本地快照。
6. 24 小时和 72 小时只作为长时间失联的日志告警节点，不触发停服、清空用户或 reload。

## 方案比较

### 方案一：只取消同步超时后的 reload

优点是改动最少，可以避免运行中的节点因为一次同步卡住而被主动关闭。

缺点是不能解决冷启动：进程、机器或容器只要在面板故障期间重启，节点仍然无法启动。它只能降低部分中断概率，不能形成真正的离线模式。

### 方案二：部署备用面板或控制面代理

优点是能提高控制面的可用性，并让节点继续获得实时变更。

缺点是需要额外基础设施、数据同步和故障切换机制，仍没有消除节点对控制面的启动依赖。它可以作为后续系统级增强，但不替代节点本地兜底。

### 方案三：持久化最后成功快照并故障开放

这是采用的方案。它同时覆盖运行中失联和冷启动失联，改动集中在 `v2node`，不要求 `v2board`、数据库或部署架构同步变更。

## 总体架构

新增一个职责单一的离线状态存储组件。每个配置节点都有独立的最后成功快照，controller 只通过该组件加载或保存状态，不直接拼接文件路径或处理原子写入细节。

默认状态目录为 `/etc/v2node/offline-state`。配置增加可选的顶层 `StatePath`，用于 Docker 或自定义部署覆盖目录。每个快照文件按规范化后的 `ApiHost` 与 `NodeID` 生成稳定标识，避免同一进程内多个节点互相覆盖。

快照包含：

- 格式版本；
- 规范化后的 `ApiHost` 和 `NodeID`；
- 最后成功保存时间；
- 完整 `NodeInfo`；
- 用户列表；
- IP 在线统计；
- 设备在线统计；
- 用户增量同步序号。

快照可能包含 TLS、DNS 或节点私密配置，因此目录只允许服务用户访问，文件权限固定为 `0600`。保存时先在同目录写入临时文件、完成同步并关闭文件，再原子替换正式文件。请求失败、解析失败、应用失败或身份不匹配时不得覆盖旧快照。

## 启动流程

每个节点启动时采用“在线优先、快照兜底”：

1. 先读取并校验与当前 `ApiHost + NodeID` 匹配的本地快照，但暂不启用。
2. 正常请求面板节点配置。
3. 面板配置请求成功时使用在线配置；失败时使用有效快照中的 `NodeInfo`。
4. 正常请求用户列表和在线统计。单项请求失败时使用同一快照中的对应数据。
5. 只有在线数据或快照能够组成完整运行状态时才启动代理内核。
6. 完全在线启动成功后保存新快照；混合使用在线数据和旧快照时先继续服务，待后续同步全部成功后再刷新快照。
7. 首次安装既无法访问面板又没有有效快照时，明确记录“无可用离线快照”并保持启动失败，禁止合成空节点配置。

有效快照中的空用户列表属于完整状态，可以启动一个没有授权用户的节点；`nil`、损坏或身份不匹配的用户状态不视为有效快照。

## 运行中失联流程

运行中任何面板读取或上报失败都只影响本轮控制面操作：

- 保持 controller、代理内核、用户列表和 limiter 不变；
- 不调用 `applyUserList` 写入失败结果；
- 不删除用户、不关闭连接、不触发 reload；
- 保持周期任务运行，在下个周期继续尝试；
- 首次连续失败时记录进入离线模式；
- 连续失联达到 24 小时和 72 小时时输出升级告警，之后限频记录；
- 任一轮完整同步成功后记录恢复在线，并清除连续失联计时。

通用周期任务增加明确的超时策略。面板同步和流量上报任务超时后只返回错误并重试，不再发送 reload 信号；确实需要通过 reload 恢复的非面板任务可以显式启用原有策略，避免无意改变其他任务语义。

## 配置变化与恢复流程

当面板恢复并返回新的用户增量或完整用户列表时，继续使用现有的差异应用逻辑。只有 `applyUserList` 成功后才推进同步序号并保存新快照，避免把未生效状态持久化。

当面板返回新的节点配置并要求 reload 时，先把新 `NodeInfo` 与当前已生效用户状态写入快照，再发送 reload 信号。这样即使面板在 reload 窗口内再次不可达，新进程也能使用刚保存的状态启动，不会因为“先关旧节点、再请求面板”而永久掉线。

恢复同步后，面板最新状态可以删除、封禁或修改离线期间继续使用的用户；这些变化从恢复成功时开始生效，不追溯中断离线期间已经发生的连接和流量。

## 一致性与安全边界

- 离线模式明确选择可用性优先，因此无法保证面板侧封禁、流量额度和权限变更的实时性。
- 快照只保存节点运行所需状态，不保存本地配置文件中的面板 API Key；快照内已有的节点私密字段按敏感文件保护。
- 快照带格式版本。未知版本、非法 JSON、关键字段缺失、`ApiHost` 或 `NodeID` 不匹配时拒绝加载并保留文件供排查。
- 多节点快照分别写入，单个文件损坏不影响其他节点。
- 保存失败只记录错误，不中断已经运行的数据面，也不删除旧快照。
- 离线状态不修改订阅生成、数据库、`v2board` API 或客户端行为。

## 可观测性

日志需要区分以下状态，避免面板告警被误判为代理停服：

- 在线启动成功；
- 使用离线快照启动，包含快照保存时间和节点标识，不输出用户、IP、Token 或私密配置；
- 首次进入离线模式；
- 连续离线 24 小时和 72 小时；
- 快照保存失败或快照损坏；
- 面板通讯恢复以及离线持续时间。

重复请求失败日志需要限频，避免面板长时间故障再次造成磁盘日志洪泛。

## 测试策略

实施按测试驱动进行，至少覆盖：

1. 快照保存与加载能完整往返节点配置、用户、在线统计和同步序号。
2. 临时文件加原子替换不会用失败写入覆盖最后成功文件。
3. 格式版本、节点身份、损坏 JSON 或缺失关键字段不匹配时拒绝加载。
4. 在线启动成功后生成快照。
5. 面板不可达但存在快照时能够冷启动并保留用户。
6. 面板不可达且没有快照时返回明确错误。
7. 运行中同步失败或任务超时不会发送 reload、不会改变用户列表。
8. 用户差异应用成功后更新快照；应用失败时旧快照和同步序号保持不变。
9. 新节点配置触发 reload 前已经落盘，因此 reload 窗口再次失联仍可启动。
10. 恢复通讯后应用最新面板数据并退出离线状态。

验证以目标 Go 单元测试、相关包测试、`go test ./...` 和 `git diff --check` 为主，不启动真实节点服务，不连接生产面板。

## 明确不做的范围

- 不建设第二套面板、数据库副本或控制面代理。
- 不在离线期间本地计算用户流量额度或模拟面板封禁。
- 不修改 `v2board`、管理后台、用户站或客户端。
- 不承诺首次安装在从未成功同步过面板时离线启动。
- 不因快照超过 24 小时、72 小时或任何固定时长而停止服务。
